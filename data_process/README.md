# NAVSIM Data Processing

This directory converts raw NAVSIM logs, camera blobs, AutoDrive-P3
annotations, and optional reasoning traces into the Hugging Face datasets used
by the Qwen2.5-VL SFT and EasyR1 RL launchers. The public pipeline is
parameterized and writes generated files outside the code checkout.

## Required inputs

Set these variables before running the pipeline:

```bash
export NAVSIM_ROOT=../data/navsim
export DATA_ROOT=../data/autodrive_processed
export ANNOTATION_ROOT=../data/autodrive_annotations
```

`NAVSIM_ROOT` must contain `navsim_logs/trainval`, `navsim_logs/test`,
`sensor_blobs/trainval`, and `sensor_blobs/test`. `ANNOTATION_ROOT` must
contain `transfusion_outputs_train` and `transfusion_outputs_test`, with one
`reasoning_trace.json` file per sample. The released
`1_RL_{train,test}_672_168.json` annotations are distributed from
[`Data`](https://huggingface.co/yuki-hahaha/AutoDrive-P3_with_Run-then-walk/tree/main/Data),
not stored in Git. Download them into `<data-root>/AutoDrive_P3/`; the
recommended layout is `../data/AutoDrive_P3/`. Set `AUTODRIVE_P3_ROOT` if the
downloaded files are placed elsewhere.

## One-command pipeline

The default resolution is `672x168`, which is the Qwen2.5-VL patch-aligned
shape and produces videos with four frames at 2 FPS:

```bash
bash data_process.sh --item all --x 672 --y 168 --workers 8
```

Use `--item train` or `--item test` to build one split. The script validates
the raw input directories, sets `DATA_PROCESS_WORKERS`, and runs these stages:

1. Filter NAVSIM logs with `navtrain.yaml` and `navtest.yaml`.
2. Export per-frame JSON and stitch the three camera views.
3. Encode four-frame history videos and add trajectory/velocity fields.
4. Merge annotations, solutions, and reasoning traces.
5. Save batched `datasets.Dataset` objects with `save_to_disk()`.

All outputs are placed under `${DATA_ROOT}`:

```text
${DATA_ROOT}/
  0_get_useful_{train,test}_scenes.pkl
  1_get_json_{train,test}/
  2_0_get_all_frames_{train,test}_672_168/
  2_1_get_all_videos_{train,test}_672_168/
  3_0_get_traj_heading_{train,test}_672_168/
  3_1_get_v_{train,test}_672_168/
  4_data_672_168/
    0_{train,test}.json
    1_{train,test}_processed.json
    2_cot_{train,test}.json
    3_cot_solution_{train,test}.json
    hf_cache_{train,test}_CoT_Solution/
```

The final `hf_cache_*` directories are the inputs for SFT. For RL, use
`rl/scripts/prepare_rl_data_step1.py` and `prepare_rl_data_step2.py` when your
annotations are in the compact RL JSON format; those scripts also write only
to paths explicitly supplied on the command line.

## Individual stages

Every stage accepts `--item train|test` and, where image dimensions matter,
`--x` and `--y`. For example:

```bash
python 2_0_get_all_frames.py --item test --x 672 --y 168
python 2_1_get_all_videos.py --item test --x 672 --y 168
python 4_4_build_hf_cache.py --item test --x 672 --y 168
```

The scripts intentionally do not source an `env.sh` file and do not contain
machine-specific home-directory fallbacks. This makes the same code usable on
local workstations, clusters, and containers.

## Coordinate and metric conventions

Bounding boxes use the stitched `672x168` image coordinate system. Trajectory
points are ego-local `[x, y, heading_radians]`, sampled every 0.5 seconds,
with four history points and eight future points. PDMS metric caches are not
generated by this pipeline; set `NAVSIM_METRIC_CACHE` to an external cache
directory when running RL or the PDMS evaluation in `../inference/`.
